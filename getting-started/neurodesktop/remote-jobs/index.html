Submit jobs to a remote HPC

Use neurodesk-jobs from a Neurodesktop terminal to send a containerized analysis to a remote Slurm cluster. DataLad transfers the selected inputs, software image, and results over SSH. You do not need Globus or a persistent cluster agent.

Experimental CLI

This pilot is included in new Neurodesktop image builds. The Bunya and Sherlock profiles are configuration templates, not validated site integrations. Complete the site checks below with synthetic or public data before using research data. There is no graphical job submission interface.

The workflow is:

Accepted jobs can finish and publish while Neurodesktop is closed. Staging and collection need an active SSH connection. Archiving runs in Neurodesktop after collection and can then work without a cluster connection.

Before you start

Section titled “Before you start”

Open a Terminal in Neurodesktop’s JupyterLab as your normal notebook user, without sudo, and check:

If the helper is missing, update to an image that includes the remote jobs feature. DataLad also needs a configured Git user name and email address.

You need:

  • An SSH account and Slurm allocation on the cluster, including working scheduler accounting through sacct.
  • Python 3.10 or newer, Git, git-annex, DataLad, Slurm commands, and Apptainer at the cluster locations configured in your profile. Compute nodes need access to the worker tools and shared storage.
  • A saved, clean DataLad dataset and a locally readable Apptainer/Singularity SIF image containing your analysis software. The desktop’s installed packages are not automatically available inside that image.
  • Persistent client storage for the profile, job records, and collected data; shared cluster storage for job records and temporary data; and a persistent archive destination mounted on the client.

Choose a project directory on persistent storage. The examples assume /neurodesktop-storage is a persistent mount in your installation; change this path if your installation uses another location.

Configure the cluster

Section titled “Configure the cluster”

Copy a template to your project:

For Sherlock, copy sherlock.json from the same directory instead. Edit the copy and replace every placeholder. The CLI rejects incomplete profiles.

Profile fieldWhat to configure
nameA short name for this site profile.
host, transfer_hostAliases in your ~/.ssh/config. They may be the same. A transfer host must permit Git and DataLad remote commands, not only SFTP.
state_rootA private, shared persistent cluster directory for submission records and helpers. It must work across login nodes; do not use node-local /tmp or purgeable scratch.
store_rootA private DataLad RIA directory store at the same absolute path on command, transfer, and compute nodes. RIA stores Git metadata and file content without a separate server.
work_rootA private cluster directory for job workspaces. Keep it separate from both the store and job records.
archive_rootA persistent directory mounted inside Neurodesktop, with enough space for selected inputs, the SIF, and results. A remote-only cluster path is insufficient.
path, python, apptainerExplicit cluster tool paths. The helper does not assume modules or CVMFS are configured. Git and git-annex must also be discoverable in the transfer host’s noninteractive SSH environment.
resourcesSlurm time, mem, and cpus-per-task; optionally account, partition, qos, and gres.
scratch_retention_daysThe applicable retention window confirmed with your site. This setting does not prevent purging.

Use absolute paths in the JSON; shell variables such as $HOME are not expanded. The cluster state, store, and work directories must be separate, not nested. Confirm filesystem permissions, atomic directory operations across login nodes, quotas, and retention with your site. For Bunya, keep active Git/RIA work outside QRISdata and choose an archive destination allowed by your project’s RDM policy.

Configure SSH using the current UQ RCC guidance or Sherlock connection guidance. Keep passwords and private keys out of the profile. Authenticate interactively:

connect opens SSH connections for subsequent commands to reuse, including after interactive MFA where supported. doctor checks login and transfer tools. It does not establish compute-node compatibility, successful MFA reuse throughout a transfer, or storage durability. Run connect again if authentication expires. Jobs receive no forwarded SSH agent.

Keep the same profile and --state path for the whole run. Do not share one state directory among independent desktops or edit a run’s profile after preparation.

Inputs and required outputs are exact relative file paths; directories and glob patterns are not supported. Include every script, template, and other file your analysis needs. Installed subdatasets and annexed files are supported; ordinary symlinks are rejected. Commands are argument lists, not shell snippets: put a pipeline in a saved script. Required outputs must be nonempty. Names including execution.json, outcome.json, and worker.log are reserved for job records.

The worker mounts the selected data at /inputs read-only and writes results to /outputs. Validation sees outputs read-only and must exit with status zero when scientific expectations pass. It should check more than file existence.

Preparation saves a new snapshot with the selected input content, source Git histories, image, commands, and checksums. Only selected annexed content is included; Git bundles also retain the source repository histories and their Git-tracked file contents. The worker retrieves staged data from the cluster filesystem, rather than following upstream dataset URLs. Each run makes its own snapshot, so allow space for multiple copies of inputs and software.

Submit and monitor

Section titled “Submit and monitor”

Copy the run_id returned by prepare:

stage transfers the snapshot over SSH. submit asks Slurm to schedule it; a job ID means acceptance, not successful analysis. The worker verifies inputs before running, validates the analysis, and publishes a separate output dataset for each attempt. Submitted jobs do not need the desktop to stay open.

Check status afterwards: cancellation is not complete until Slurm confirms it.

State or evidenceWhat it tells you
stagedTransfer finished; worker verification is still pending.
submission-unknownSlurm acceptance is uncertain. Reconnect and inspect status; repeating submit does not create another job.
Attempt inputs-missingRequired staged content could not be verified; analysis did not start.
Attempt site-results-availableResults were published and verified on cluster storage.
Slurm COMPLETED, exit 0:0, and a valid result receiptResults are eligible for collection.
collection.json / archive.jsonClient retrieval / archive restoration was verified.

If submission remains uncertain, reconcile it using scheduler evidence and site support. Do not delete the job records to retry. A new prepare creates a distinct run and could duplicate work already accepted by Slurm. Timeout, cancellation, out-of-memory failure, or an unknown scheduler state cannot count as success just because some output files exist.

Retrieve and preserve results

Section titled “Retrieve and preserve results”

After the job completes, reconnect if needed, then run:

Collection verifies the result content and execution inputs. Results are under $PROJECT/job-state/runs/$RUN_ID/collected/output/; the example writes summary.json there. The client selects one successful attempt and reports any others without merging them.

archive writes a bundle to the profile’s archive_root, restores it into a fresh directory, and verifies content and provenance before issuing a receipt. The bundle includes the selected inputs, source Git histories, SIF, outputs, and job records. It refuses to overwrite an existing archive. Already collected results can be archived even after cluster accounting expires.

Use the archive path returned by archive to restore to a new directory:

Restoration needs DataLad, Git, and git-annex, but no cluster connection or original scratch store. Verify that your archive destination has the retention and backup policy your project needs. This pilot does not upload to a remote-only RDM service.

Collect before scratch expires

Jobs can publish while the desktop is off, but collection and archiving happen only when you reconnect. Results can be lost if scratch is purged first. Scratch copies are not trusted as preservation copies, and the helper never automatically drops data or removes old attempts. Plan both byte and inode capacity, and retain an independent copy of your source inputs.

Validate Bunya or Sherlock before research use

Section titled “Validate Bunya or Sherlock before research use”

Use the template for your site and record tests with synthetic or public data:

  • One interactive login reused across staging and collection, including disconnect and reauthentication, on the actual command and transfer hosts.
  • Job records visible across login nodes and concurrent submission retries without automatic duplicate jobs, including a lost submission response.
  • Compute-node execution and publication from staged inputs without external transfers or credentials, with a compatible SIF and working tool paths.
  • Concurrent attempts, cancellation, timeout, missing inputs, and publication failure reported accurately; desktop shutdown followed by successful collection.
  • Archive restoration after the scratch copy is unavailable, with confirmed permissions, retention, and capacity for each storage location.

The implementation reference and full acceptance checklist cover the remaining failure scenarios and cross-site comparison tolerances. The existing Bunya and Sherlock guides describe running Neurodesk on those clusters; those installations do not by themselves validate this remote submission workflow.
